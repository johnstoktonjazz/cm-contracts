# Контракт `geopackage` 1.1.0: геопакет проекта

**Владелец:** картограф. **Пишет:** картограф (`ingest`, `fetch`, `analysis`). **Читает:** база (объекты, `fact_ids`, статусы), расчетчик (геометрия для буферов и подсчетов), верстка (не читает напрямую — получает карты по контракту `image`).

Схема описывает содержимое одного файла `.gpkg` в виде JSON-выгрузки; `example.json` — такая выгрузка для теста. Картограф проверяет файл по схеме при каждой сборке.

## Что зафиксировано

- Один файл — одна система координат из `project.yaml` (`crs.name`; EPSG-код или МСК с параметрами). Пересчет внешних источников при импорте.
- Перечень слоев закрытый, у каждого слоя одна геометрия: площади — `MultiPolygon`, линии — `MultiLineString`, точки — `Point`. Новый слой или поле — новая версия контракта. Пустые слои допустимы.
- У каждого объекта: `object_id`, `kind`, `status`, `source_label`, `source_date`, `fact_ids` (пустой список, если записей нет). У `reference` — еще `source_license`, у `digitized` — `digitized_from`.
- Шесть статусов: `official`, `cadastral`, `digitized`, `concept`, `reference`, `calc` (расчет картографа: изохрона, буфер — с `CALC`/`NORM`/`ASM` в `fact_ids`, лицензия исходных данных в `source_license`). Статус повышается только документом. Те же имена — в `image` и `overlay`.
- `fact_ids` связывает объект с реестром базы: площадь по ТЭП — факт, а не измерение по контуру.
- Атрибуты — закрытый перечень по слою (таблица ниже), имена латиницей.
- Времени сборки в файле нет: вместо него `input_hash`. Та же сборка — тот же файл.

| `boundary_planning` | MultiPolygon | граница проекта планировки | — |
| `red_lines` | MultiLineString | красные линии | `state` |
| `blocks` | MultiPolygon | кварталы: по ППТ (`official`) или по улично-дорожной сети (`reference`) | `num` |

| `roads` | MultiLineString | улично-дорожная сеть | `road_class`, `tunnel` |
| `rail` | MultiLineString | железные дороги и трамвай | `rail_class`, `tunnel` |
| `transit_stops` | Point | остановки и станции | `mode` |
| `buildings_osm` | MultiPolygon | существующая застройка по внешним источникам | `floors`, `building_use` |

| `heritage` | Point | ОКН; территории и зоны охраны — в `zouit` | `registry_number`, `category` |
| `accidents` | Point | ДТП, без персональных данных | `date`, `severity` |
| `isochrones` | MultiPolygon | зоны доступности по графу | `mode`, `minutes`, `speed_kmh`, `origin_id` |
| `buffers` | MultiPolygon | буферы ограничений и зоны счета | `buffer_type`, `distance_m`, `origin_id` |
| `concept_objects` | MultiPolygon | проектируемая застройка концепции | `num`, `purpose`, `floors` |
| `concept_sites` | MultiPolygon | участки концепции | `num` |

Значения перечней — в `schema.json`. Словари `kind` — `kinds.yaml` (с этапом 1 картографа).

Слои геопакета — данные; слои стандарта карты верстки (`cm-design/tokens/map.yaml`: `territory`, `road_main`, `point_1`, `zone_sanitary` …) — роли на карте. Описание карты картографа связывает одно с другим: роль ← слой геопакета и отбор (`roads` с `road_class = 'main'` → `road_main`; `zouit` с `zouit_type = 'sanitary'` → `zone_sanitary`). Поэтому `zone` и `code` у зон названы как поля стиля `zoning.qml` верстки.

## `object_id`

Вид `слой:ключ`, уникален в файле. Ключ берется из источника, а не из порядка записи, поэтому не меняется между сборками:

| Источник | Ключ | Пример |
|---|---|---|
| ЕГРН | кадастровый или реестровый номер, `:` → `-` | `parcels:00-00-000001-12` |
| OpenStreetMap (напрямую или через Overture) | тип и номер элемента OSM | `roads:osm-w100200300` |
| Overture без OSM | идентификатор GERS | `poi_other:ovt-08f2…` |
| реестры (ОКН, bus.gov.ru, гостиницы) | номер записи реестра | `heritage:612410025360006` |
| чертеж DXF | номер из документа, если правило раскладки его читает (квартал, участок, индекс зоны); иначе `g` и 12 знаков SHA-256 геометрии, округленной до 1 см | `blocks:2`, `red_lines:g3fa9c01b27de` |
| анализ | параметры расчета и ключ исходного объекта | `isochrones:walk-15-transit_stops-osm-n700800900` |

Ключ по геометрии меняется вместе с геометрией: это уже другой объект. Отчет `ingest` перечисляет исчезнувшие и новые `object_id` против прошлой сборки — база перепривязывает `fact_ids` по нему. Два объекта с одним ключом — ошибка сборки.

## Хранение в GPKG

- Каждый слой — таблица с именем слоя, геометрия — столбец `geom`, одна система координат на все таблицы.
- Общие поля и атрибуты слоя — обычные столбцы с теми же именами (без `attrs.`): стили QGIS и запросы читают их напрямую. `fact_ids` и `confirmed_by` — текст с JSON-массивом (`["F-000412"]`, `[]`).
- `object_id` — столбец с уникальным индексом; `fid` служебный и ничего не значит.
- Таблица `cm_meta` (`key`, `value`, тип `attributes` в `gpkg_contents`): `contract`, `project`, `crs`, `input_hash`.
- Даты изменения в `gpkg_contents` пишутся постоянными, иначе файл различался бы при каждой сборке.

## Что запрещено

- Объект без статуса или источника; `reference` и `calc` без лицензии.
- Лицензия — у каждого объекта (`source_license`), не у файла: геопакет смешивает источники (ответ Романа, ODbL).
- Слои с данными, запрещенными к печати по лицензии (Яндекс, 2ГИС, Google).
- Правка геометрии руками в QGIS с сохранением в выпускной геопакет: только через `ingest` и правила.
- Персональные данные из ЕГРН (правообладатели) и из карточек ДТП: только номер, граница, вид использования, дата и тяжесть.
